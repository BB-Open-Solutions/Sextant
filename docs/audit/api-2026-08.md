# API audit, August 2026

Read against `main` on 2026-08-07, before 1.0.0. Every claim below was
measured against the code or the running deployment. Where an assumption of
mine turned out wrong, it says so.

Scope: the operator API (`/api/v1/*`), 56 operations. The device-facing
endpoints (`/api/checkin`, `/api/station/*`, `/api/device/*`) are a separate
contract with different clients and are covered only where they differ.

## Findings

### A1 - The OpenAPI spec documents paths and nothing else

**Measured.** `internal/http/api/openapi.json` carries 56 operations. Of
those:

- **0 have a response schema.**
- **0 component schemas** are defined.
- The only status codes documented anywhere are **200 and 201**.

The API itself uses twelve: 200, 201, 204, 400, 401, 403, 404, 409, 410,
413, 422, 500 (counted from `http.Status*` in the handlers).

**What this costs.** A client generated from this spec has no types and no
error handling. Every 4xx is a surprise. For a municipality that is exactly
the artefact they will ask for during procurement, and the one an integrator
will generate a client from on day one.

**Severity: medium, and the highest-value item in this audit.** It is also
the least risky to fix - documentation cannot break a running fleet.

**Half closed, 2026-08-07.** Every operation now documents the refusals it
can produce - 401, 403, 404 and 500 everywhere, plus 400, 409, 422 and 503
on writes - all pointing at one `Error` schema, which is what
`API.fail` actually writes. The error half was done first on purpose: a 422
is what an integrator hits on day one, and a perfect device schema does not
help them handle it.

Two tests keep it true. One asserts the floor per operation and that each
error points at the shared schema; the other calls the server, takes a
documented 401, and checks the body is exactly `{"error": "..."}` - because
a documented shape the server does not write is worse than no documentation.
Verified by mutation: turning one error back into plain text fails them.

**Still open: the SUCCESS schemas.** A client still has no types for what an
endpoint returns on 200. That is the larger half by volume and the smaller
half by urgency.

**Not a criticism of what exists.** The path/method coverage is verified in
both directions by `TestOpenAPIContract`, which is better than most projects
manage: an endpoint added without a spec entry fails CI, and a spec entry
without an endpoint fails too. The gap is depth, not drift.

### A2 - No pagination on any list endpoint

**Measured.** Exactly one query parameter bounds a result set in the whole
API: `limit` on `/api/v1/audit` (`me.go:100`). Every other list returns
everything:

`/api/v1/devices`, `/api/v1/fleet`, `/api/v1/changes`, `/api/v1/hostkeys`,
`/api/v1/secret-refs`, `/api/v1/access`, `/api/v1/directory/groups`.

**Scale, measured rather than guessed.** A device record on
`/api/v1/devices` is about 80 bytes today (`{"tag":...,"groups":[...],
"class":...,"hardware":...}`). At Zaanstad's order of magnitude that is
tens to hundreds of KB per call - annoying, not fatal. `/api/v1/fleet` is
the one to watch: it returns the whole document including every scope's
settings, and that grows with configuration rather than with device count.

**Severity: low today, and it is a 1.0 decision anyway.** Adding pagination
after the freeze is a breaking change to every list endpoint unless the
parameters are opt-in. Deciding the shape now - even if the default stays
"everything" - costs nothing and keeps the option.

### A3 - Middleware errors are plain text, handler errors are JSON

**Measured.** Handler errors go through `API.fail` (`api.go:203`), which
writes `{"error": "..."}` with a status per error class - authorisation 403,
gate rejection 422, lost write race 409, dependency gap 503, bad input 400.
That is consistent and structural, and it is the good part.

Five paths bypass it, all in the wrap middleware, all before the handler
runs (`api.go:154-183`): api disabled, unauthorized, read-only server,
missing CSRF token, no role grants access. They use `http.Error`, so they
answer `text/plain`.

A client that parses `{"error":...}` therefore succeeds on a 403 from a
handler and fails to parse a 401 from the middleware - which is the most
common error a new integrator will meet first.

**Severity: low, but it is cheap and it is the first impression.**

**CLOSED 2026-08-07.** All five now go through `writeJSON`.

Fixing it turned up a sixth that I had not looked for: a path matching no
route at all answered Go's default `404 page not found` in `text/plain`. A
typo'd path is the most ordinary mistake an integrator makes, and it was the
one case that broke the contract hardest. There is now a JSON catch-all
under `/api/v1/`, registered as the least specific pattern so every real
route still wins.

One case is honestly still plain text: a METHOD mismatch (POST to a GET-only
path) is ServeMux's own 405 and cannot be overridden without routing every
method by hand. It is a smaller trap - the path exists, so the client is
closer to right - and it is written into the code rather than left to be
rediscovered.

### A4 - No documented versioning or deprecation policy

The spec's description says *"Additive-only after the 1.0 freeze"*, and
ADR 0004 says the API is "designed and versioned deliberately from phase 2
on". That is a position, and it is the right one, but it is a sentence in a
description field rather than a policy.

Missing: what happens when something genuinely must change, how long a
deprecated field lives, and whether `/api/v2` is the answer or a header is.
A municipality's integrator will ask, and "additive-only" alone does not
answer it.

**Severity: low technically, medium contractually.**

## Checked and sound

Recorded because an audit that lists only failures misrepresents the thing.

- **Error semantics are classified, not improvised.** `API.fail` maps error
  KINDS onto statuses in one place, so a handler returns a typed error and
  the status follows. The distinction between 422 (the gate refused this
  configuration) and 400 (you sent nonsense) is real and deliberate, and
  `settingErr` documents why.
- **Rate limiting covers the operator API.** I assumed it did not and was
  wrong: `/api/v1/` is behind 20 rps / burst 40, the device check-in behind
  the same, and the station endpoints behind 5 rps / burst 10
  (`capabilities.go:607,629,740`).
- **Request bodies are bounded everywhere.** Every decode path runs through
  `http.MaxBytesReader`, with a cap chosen per path: 1 MiB for the API,
  4 KiB for device auth, 320 KiB for a check-in, 4 MiB for a station report
  and a diagnostics bundle.
- **Writes are guarded rather than idempotent, and that is the right
  choice here.** Enrolling an existing tag is refused rather than treated as
  an update - a second enrolment would re-issue a credential and silently
  invalidate the one already running on the machine. Same for a second
  concurrent rollout, an already-merged change, an already-abandoned change.
  Refusing is the safer semantic for operations whose repetition is almost
  always a mistake.
- **Authentication is uniform.** One bearer path for tokens, one session
  path with CSRF on mutations, both resolved in the same wrapper. No
  endpoint authenticates its own way.
- **The spec cannot drift from the routes.** `TestOpenAPIContract` compares
  both directions and fails CI on either.

## Order of work

1. **A1**, and specifically the error responses before the success schemas.
   Documenting that a 422 carries `{"error": "..."}` is more useful to an
   integrator than a perfect device schema, because it is what they hit
   first.
2. **A3**, half an hour, and it makes A1's error documentation true for
   every path rather than most.
3. **A4**, a paragraph in the spec description plus a line in the roadmap.
4. **A2** as a 1.0 decision: agree the parameter shape even if the default
   behaviour does not change.

None of these blocks a fleet from running. All four are what a procurement
process asks about, which is a different bar and the one Zaanstad brings.
