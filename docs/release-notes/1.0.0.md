# Sextant 1.0.0 - release notes

**DRAFT. Not released.** The tag is cut when the seven gate items in
`1.0-fit-gap.md` are closed; four were open on 2026-08-10. This document is
written ahead of that so the release is described by somebody who was there,
rather than assembled from a commit log the week it ships.

A note on what this is. There is no `CHANGELOG.md` in this repository and
this document does not start one: a hand-maintained list beside the git log is
a second list to keep in step, and that is how the old roadmap drifted from the
fit-gap. This is a **milestone document**, written once, for the reader who
will not read 300 commits - a procurement officer, an auditor, a municipality's
architect.

## What Sextant is

A control plane for a fleet of NixOS workstations, run by the organisation that
owns the fleet. Every device's configuration is data in a git repository the
customer holds. Nix builds it, a gate proves it compiles before anyone can
merge it, and the fleet rolls forward in rings with soak times and health
thresholds.

**Devices pull.** The console has no channel that executes on a device
(ADR 0023). That is the security property the product is built on, and it is
also the reason a classic MDM wipe is impossible here - what we offer instead
is a cryptographic wipe that lands at the next boot, and we say so rather than
implying an immediacy we do not have.

## What 1.0 contains

The gate in `1.0-fit-gap.md` is the authoritative list. In summary:

- **Configuration**: settings resolving organisation → group → device with
  locks; policies with control annotations an auditor can read; conditions on
  observed state that are checked rather than enforced.
- **Change and rollout**: a nix gate that must pass before a merge, optional
  four-eyes approval, ring-based rollout with soak, health thresholds, pins
  and stall detection.
- **Devices**: imaging from a provisioning station at the ring's pinned
  revision, declarative remote intents (lock, diagnostics, crypto-wipe),
  secrets with agenix, LUKS recovery-key escrow with audited reveals.
- **Evidence**: an audit trail that is the git history, evidence and CSV
  exports, per-policy BIO/ISO annotations, scoped access.
- **Integrations**: NetBird, directory login over LDAPS with SSSD, Wazuh
  agent enrolment, OpenBao, SMTP.

## What is deliberately not in 1.0

Recorded in `1.0-fit-gap.md` §6 and repeated here because a release that only
lists what it has is marketing:

- Full HA OpenBao with auto-unseal and TLS. Scoped by ADR 0018: the vault is
  load-bearing only for secrets classified *Revocable*, so a fleet whose
  secrets are all *Autonomous* keeps working with the vault down.
- Sovereign flake mirrors and our own binary cache as fleet substituter
  (ADR 0016 is a draft; the fork exists as phase one).
- Forge drivers. Provisioning is manual by decision.
- SCIM inbound, and LDAP direct-bind as a console auth source.

## What is honest about it, and this section is the point

Every item here is measured, dated and documented elsewhere in this
repository. A municipality evaluating this deserves them in one place rather
than distributed across four audits.

- **No per-device CVE view.** `nix run sextant#fleet-sbom` produces an SBOM
  and a cross-referenced vulnerability report per distinct fleet closure, off
  device and per configuration rather than per machine. It is not continuous
  and there is no dashboard. Note also that **Wazuh's own vulnerability
  detection does not work on NixOS** - it reads a dpkg inventory that does not
  exist, so it reports every device clean. That is a false negative that reads
  like a pass, and it is why the SBOM route exists.
- **The accessibility statement is not published.** The mechanical half of
  WCAG 2.2 AA is fixed and held by a test - 73 unlabelled form fields and 11
  icon-only buttons went to zero on 2026-08-07, and a new one fails the build.
  The manual round (keyboard, screen reader, contrast, 400% reflow) has not
  been done and has no owner. A statement claiming more than has been tested
  is a false declaration, so the draft says "partially compliant" and stays a
  draft.
- **DPIA and processing agreement are drafts.** Written by the people who know
  where the data is, so the question to a DPO or a lawyer is "is this right"
  rather than "please make this". Neither is approved or signed.
- **The sealing key is not in the backup.** The observed plane is backed up
  off-cluster and the restore path has been walked - counts matched and the
  md5 of all LUKS ciphertext came back identical on 2026-08-07. That proves
  the backup is complete and restorable. It does not prove the recovery keys
  can be *opened*: that needs `SEXTANT_SECRET_KEY`, which is not in the backup
  and whose management is not yet assigned to anyone.
- **A device follows one forge.** `comin` polls a single remote and the
  overlay repository has no mirror. Losing the forge does not break the fleet -
  every machine keeps running - but nothing can be changed on any device until
  a forge exists again at the same URL. Recorded as an accepted risk in
  `docs/runbooks/disaster-recovery.md`, with the fix noted: comin's remotes is
  a list.
- **Losing the console stops intents.** Convergence goes to the forge, so a
  console outage does not change what any machine runs. Check-ins, elevation,
  imaging and every remote intent do stop - which means **a lost laptop cannot
  be wiped while the console is down.**
