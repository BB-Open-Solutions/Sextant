Status: living document, re-verified against the **0.80.0** code on

It **supersedes** the earlier roadmap and MVP notes, both now removed —

## How to read this

- **READY** = built, tested, running.
- **GAP** = genuinely remaining; each names the concrete work.
- Integration readiness is split into device-side module, console
  surface, backend, network route, and end-to-end proof, because those
  advance independently.

## 1. The app, standalone

### 1.1 Configuration plane — READY

Config is data, never code (ADR 0005). The console/API only ever writes
`fleet.json` (and, for the expert path, an overlay module that must
evaluate — see 4.2). Every write runs one serialized transaction
(`internal/app/config.go`, `applyTx`): decode → mutate → re-encode →
write → **gate.Validate** → commit on pass, restore + `ValidationError`
on fail. The nix gate is the injection firewall: it forces each affected
host's `config.system.build.toplevel.drvPath` through `nix eval`
(`internal/adapters/nix/gate.go`), running the generator's injection-safe
asserts and the whole NixOS module system, so an unknown option, wrong
type or injection attempt fails before commit. The only strings spliced
into nix are host-name slugs, regex-constrained
(`^[a-z0-9][a-z0-9-]{0,62}$`) and `%q`-quoted at every splice point; exec
is an argv slice, no shell. The remote gate-runner (ADR 0012) runs the
eval out-of-process, fail-closed; **production runs `gateMode: remote`**.

### 1.2 Updates / rollout — READY

Staged waves with soak + health gates; the org sets a test group + a
ladder, everything else is an opinionated default. Delivery-on-merge
("saving IS rolling out") with scoped runs, expedited, halt/pause/cancel,
and confirmation summaries before anything irreversible. Build-before-
promote realises each release into a signed binary cache (on a PVC, so it
survives pod restarts) before a ring branch moves, so devices substitute
instead of compiling. Absent devices (a laptop shut for days) leave the
promotion denominator and catch up on their next check-in; only
demonstrated failure (`RingStatus.Broken`) trips the failure budget. Two
engine bugs (skipped branch-push on a prior credential failure; failure
budget computed over mismatched time windows) were found and fixed this
cycle.

### 1.3 Remote actions (design 0004) — READY, including the wipe

The path once deferred is built and tested end to end:
arm an intent (org Owner, an audited git commit — `internal/http/api/
intent.go`, `internal/domain/fleet/intent.go`) → the agent relays it on
its next check-in (`agent/src/action.rs`) → a root oneshot `sextant-actd`
(`deploy/nixos/actd.nix`) executes lock / reboot / provision **and the
destructive crypto-wipe** (`cryptsetup luksErase`). Wipe is gated by
three independent walls: org-Owner to arm + the audited commit; the host
must be separately `armWipe=true` (compiled into different bash at build
time — an unarmed host literally cannot erase); and the device must be
locked first. Intent is data on the device record, relayed on check-in —
no live command channel.

- **P3 — DONE.** Design 0004's explicit replay guard is implemented: the
  check-in handler signs a nonce plus timestamp onto the wipe intent and
  verifies it on ack (`internal/http/api/intent_nonce.go:32` `signIntentNonce`,
  `:45` `verifyIntentNonce`, wired at `internal/http/api/checkin.go:251-259,
  302-311`). The window was already closed by construction (intent is the
  direct HTTP response to an authenticated check-in, no store-and-forward);
  the nonce is the audit-visible acceptance criterion, and it is now there.

### 1.4 Secure Boot + TPM2 enrollment wizard (design 0001) — READY

Detect-don't-declare: the agent probes SB (efivar + sbctl store) and TPM2
(device + enroll stamp) — `agent/src/posture.rs`. The observed plane
carries the posture (migration `0004_posture.sql`, `internal/domain/
observed`), the device page shows a per-device checklist joining observed
vs the resolved target, and the imaging/provision plane actively drives
the ceremony via derived reboot/provision intents (`actd` runs
`sbctl enroll-keys` + `systemd-cryptenroll --tpm2-pcrs=7`).

- **GAP**: end-to-end proof on real Secure-Boot hardware (t495s) —
  manual, not code. Run A of the acceptance plan reached A3.11 on
  2026-08-04 and has not yet covered the ceremony rows
  (`docs/e2e-acceptance-plan.md`, A3/A4; findings so far in
  `docs/e2e-3-findings.md`).

### 1.5 Console — READY

Catalog-driven settings (the entire settings surface derives from the
overlay's documented `dawo.*` options; no hand-built toggles), profiles
(recommended per-class starting points), integrations (scoped org/group),
policies (drift-aware, reach-counted, foot-guns refused), evidence
export, audit trail, RBAC derived per request, CSRF on every mutation,
an honest 500 on a template error with a page smoke net. Human labels,
release names instead of git hashes, dependent-field greying, the
friendliness passes.

### 1.6 Security — READY (documented)

`docs/threat-model.md` is the standing model, grounded file:line, with a
residual-risk register R1–R7 (overlay eval surface, shared bridge token,
per-handler visibility, deploy credential, wipe sandbox, token group-
snapshot staleness, unsealed LUKS key when the store is off), each with
its current mitigation and close-out. Token model: argon2id (64 MiB, t=1,
p=4), timing-equalised, downward-only ceilings, no chaining, mandatory
TTL, hash-only at rest. One authorization path derived per request from
the live document.

## 2. Recommended integrations

Every integration's **device-side module and console card are DONE**. The
remaining work is backend / network route / a decision — not Sextant
code. The route decision (recommendation: **mesh** — one NetBird
routing-peer reaches LDAP + Wazuh + OpenBao) gates most of it.

| Integration | Device module | Console card | Backend | Route | E2e |
|---|---|---|---|---|---|
| **NetBird** (VPN) | READY `dawo.netbird.*` | READY | READY (management live) | GAP: cluster routing-peer | GAP: t495s peer |
| **Wazuh** (SIEM) | READY (+ packaged agent, enroll) | READY | GAP: no manager (`apps/wazuh`) | via mesh | GAP |
| **OpenBao** (key vault) | READY `dawo.openbao.*` (fetch on boot + hourly, tmpfs) | READY | READY (live in cluster) | GAP: mesh route | GAP: e2e + precedence fix (ADR 0018) |

### 2.1 NetBird — recommended VPN
Self-hosted mesh (`services.netbird`), device joins with a setup key
delivered as a secret reference. Management server live
(`netbird.bb-open.com`). Gap: a cluster routing-peer (subnet route to the
service CIDR) so devices reach internal services in one move; then the
t495s-becomes-a-peer proof.

### 2.2 Wazuh — SIEM
The device module packages the agent and enrolls it (`agent-auth`,
per-group). Gap: no manager exists — a minimal `apps/wazuh` (enrollment
1515 + agent 1514) in the platform, reachable over the mesh; then the
"agent appears in the Wazuh console, correct agent group" proof.

### 2.3 OpenBao — key vault — IN 1.0 (ADR 0018)
Live in the cluster (ns `openbao`, KV v2 mount `fleet`); the device
module (`dawo.openbao.*`) fetches named secrets on boot + hourly and
symlinks them from `/run/agenix/<name>`, so the secret-ref contract stays
backend-agnostic and rotation reaches devices with no config change.
OpenBao is **platform infrastructure**, not a Sextant component — Sextant
is its first consumer; it is intended for cluster secrets, application
stacks, Forgejo and Terraform too.

**In 1.0 by decision (2026-08-05, ADR 0018), and the shape is settled:**
every secret names exactly one backend — agenix for what a device needs
to reach a working state alone, OpenBao for what must be rotatable,
audited and revocable. Not a primary with a fallback; two stores holding
one value can disagree, and a device serving a stale secret while every
layer reports success is the failure class this release removed
elsewhere.

Remaining for 1.0: the mesh route, one secret proved end to end on
hardware, and the **precedence fix** — the fetch unit currently symlinks
only when agenix has not already claimed the name, so a secret present
in both is served from agenix and a vault rotation never arrives. A name
in both backends must be refused at the gate, not resolved silently.

Not required for 1.0: HA and auto-unseal. The vault is load-bearing only
for the secrets classified as vault-managed, so availability scales with
that list instead of being all-or-nothing.

### 2.4 Identity — two first-class surfaces
Identity is **not just console login**. Two vendor-neutral surfaces:

1. **Device login via SSSD** (`dawo.identity.*`, provider
   `ldap|ad|ipa`): end users sign in on managed laptops against the
   directory, with offline cached credentials (`cacheCredentials`,
   `offlineLoginDays` → sssd `cache_credentials` /
   `offline_credentials_expiration`). Three openldap instances live; the
   bind secret is provisioned. Gap: the route decision (mesh vs LDAPS).
2. **Console SSO via OIDC**: operators sign into Sextant. Zitadel live;
   Nubus (bundled OpenLDAP + Keycloak) available. ADR 0015 (draft)
   settles the ONE token authority per deployment and how the directory
   backs both surfaces. "Other identity apps" (Nubus/Keycloak, AD, IPA)
   plug into either surface without Sextant code changes.

The directory is the source of truth for people/groups; exactly one SSO
authority issues tokens per deployment; Sextant stays IdP-neutral OIDC.

## 3. Git backend + forge coupling — runtime is forge-agnostic

The runtime git adapter (`internal/adapters/git`) is **already
forge-agnostic**: plain `git` over a named remote (https + netrc), zero
forge-specific API calls. Sync, safe-write commit/push, and ring-branch
force-push work against ANY git remote — GitHub, GitLab, Codeberg,
Forgejo. "Bring your own forge" is a 1.0 property, not a future one. Ring
branches are machine-owned (the rollout engine is the only writer; the
force-push credential is the R4 trust concentration in the threat model).

The only forge-specific coupling is at provisioning/lifecycle time
(create the overlay repo, issue a deploy token, optionally a webhook),
which lives in the cells layer behind a small **forge driver** interface
(Forgejo driver first; others additive).

## 4. Product shape toward 1.0 (in scope)

### 4.1 Module bundles — READY
Beyond one-toggle settings: opinionated, dependency-aware bundles that
flip several `dawo.*` together and keep the few knobs that matter visible
(e.g. Identity bundle = SSSD + matching hardening, exposing the cache
choice). Built on the profiles machinery (`fleet.Profile`,
`ApplyProfile`, overlay `profiles.json`) + the `requiresOf` dependency
convention; authored as overlay data. Shipped as
`internal/domain/fleet/bundles.go` + `internal/http/web/bundle_ops.go`,
rendered on the settings page (`internal/http/web/settings.go:315`,
route `post("/settings/bundle/{name}/apply")`).

### 4.2 Advanced mode — READY
Deep configuration moves from IDE file-tweaking into the console. Both
tiers are shipped:

- **Safe package tier** over `Scope.Packages/Flatpaks/Overlays`:
  `postScopeApps` (`internal/http/web/policy_ops.go:223`, route
  `post("/apps")`) applies `fleet.SetScopeApps` through `applyGated` at
  Editor level, so an app change is gated and audited like every other
  mutation.
- **Expert-gated nix editor** for the custom overlay (`WriteOverlay`,
  ADR 0014) with a `nix-instantiate --parse` syntax-check for fast
  feedback before the full gate eval on save —
  `internal/http/web/overlays.go:93` `postOverlayWrite`, `:110`
  `postOverlayCheck`.

Every save stays gated (must evaluate) + audited; R1 covers the risk.

## 5. Multi-tenancy — cells (in scope, GAP)

ADR 0009 chose instance-per-tenant cells, GitOps-managed, with a hard
boundary between the per-tenant console and a global admin plane that
never reads customer data.

**Production is the only cell** (decision 2026-08-05). This document
previously said "two cells ship (prod + a shared-artifact demo)"; the
demo is not part of the product and is being retired. As of 2026-08-05
it was still running in the cluster on a **suspended** Flux
Kustomization, pinned at an old revision with nobody reconciling it —
an application outside GitOps is worth removing on that ground alone.
The release workflow's `-tools` image exists "because the demo tracks
the release", which stops being true with it.

The build is a clean isolated cell plus the provisioning ergonomics: a
platform-repo template directory + runbook (manual `cp`/`sed`, no
scaffolder or CLI — scope decision 2026-07-28, "less is more",
reconfirmed 2026-08-05; a reseller portal where customers create and
manage their own environments is post-1.0 and belongs in the roadmap),
plus a thin Grafana admin plane over Flux/kube-state-metrics + three
PII-free app metrics. Design in `docs/design/0005` (complete).

## 5a. High availability — multiple replicas — READY

The hard part is already done. The config write path is HA-designed: a
write serializes in-process (`writeMu`) but the cross-replica lock is git
itself — `applyTx` does sync + rebase-retry on `ErrConflict`
(`internal/app/config.go:23,188,235`, "the HA write path"). Sessions are
stateless encrypted cookies (`internal/adapters/oidc/oidc.go`), so any
replica validates any session. So the read/write API and console scale
out to N replicas today.

The committing background workers — the rollout ticker and the upstream
watcher — now run on exactly ONE replica via a **Postgres advisory-lock
leader election** (`internal/adapters/postgres/leader.go`): the holder is
the leader, and if it dies its session ends and the lock releases so a
standby takes over. No external coordinator, no new dependency - the
database the app already needs is the coordinator (keeps the deploy
simple). The sync loop and cache warming run on every replica (each keeps
its own snapshot warm). For HA the chart needs `replicaCount: N` with
`persistence.enabled: false` (the overlay is a per-replica git clone; a
RWO PVC cannot be shared) - the chart fails template rendering on the
wrong combo and adds a PodDisruptionBudget
(`deploy/helm/templates/pdb.yaml`). Tested: two leader loops never run
the worker concurrently, and failover re-elects; CI asserts the guard
actually fires rather than trusting that it exists
(`.forgejo/workflows/ci.yml:148-151`).

## 5b. Design guardrails (non-negotiable, apply to everything above)

- **Simple and user-friendly.** "Intune but extremely user-friendly."
  Every feature keeps the simple path simple; power surfaces (advanced/
  nix editor, per-package) sit behind explicit expert gates, never in a
  normal admin's way.
- **Easy to deploy on RKE2-style clusters** (the proxy-platform spec). A
  cell stays pure declarative data — one HelmRelease + Flux Kustomization
  + secret + overlay repo — no bespoke operators, no heavy dependencies.
- **HA by default** (5a): built to run multiple replicas.
- **Security is paramount.** Every new surface is re-checked against the
  threat model (R1–R7); every mutation stays gated + audited + authorized
  per request; prefer the design that adds no new trust concentration.

## 6. What is NOT in 1.0 (explicit)

- Full HA OpenBao / auto-unseal / TLS. Still post-1.0, but for a reason
  that changed: under ADR 0018 the vault is load-bearing only for
  secrets classified *Revocable*, so availability scales with that list
  instead of being all-or-nothing. A fleet whose secrets are all
  *Autonomous* keeps working with the vault down.
- Sovereign flake chain mirrors + own binary cache as fleet substituter
  (ADR 0016, draft — the fork exists as phase 1).
- Forge drivers (Forgejo or otherwise) — provisioning is manual by
  decision (design 0005 scope, 2026-07-28); a driver interface only
  returns if provisioning volume ever demands it.
- SCIM inbound; LDAP direct-bind as a console auth source (optional).
